# Feature Specification: 将棋定跡管理アプリケーション（Joseki Manager）

**Feature Branch**: `002-joseki-manager`
**Created**: 2026-01-12
**Status**: Draft
**Input**: 将棋の定跡を管理するアプリケーション。フローチャート/木構造風UIで序盤定跡を管理し、戦型ラベル付けによる知識整理を可能にする。

## 概要

個人学習を目的とした将棋の序盤定跡管理アプリケーション。既存の棋譜管理アプリ（ShogiGUI、ぴよ将棋、Shogi Home等）が実践の棋譜管理に特化しているのに対し、本アプリケーションは序盤学習に最適化されたフローチャート/木構造形式での定跡管理を提供する。

### 想定ユースケース

- 定跡書の学習時に手順を木構造で整理・記録
- 将棋の戦術書執筆時の参照用定跡データベース構築
- 自身の序盤レパートリーの体系的管理

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 定跡ツリーの作成と手順入力 (Priority: P1)

ユーザーは新しい定跡ツリーを作成し、初期局面から分岐する手順を木構造形式で入力できる。各ノードは1手を表し、同じ局面から複数の応手を登録することで分岐を作成する。

**Why this priority**: 定跡管理の核心機能であり、これなしには他の機能が成立しない。最小限の価値を提供するMVPの基盤となる。

**Independent Test**: 定跡ツリーを新規作成し、初手から5手程度の分岐を含む手順を入力、保存、再読み込みできることを確認。

**Acceptance Scenarios**:

1. **Given** アプリケーションを起動した状態、**When** 新規定跡ツリー作成を選択、**Then** 初期局面（平手）をルートとした空の定跡ツリーが作成される
2. **Given** 定跡ツリーの任意のノード（局面）を選択した状態、**When** 指し手を入力、**Then** その手が子ノードとして追加され、木構造が更新される
3. **Given** 既に子ノードが存在するノードを選択した状態、**When** 別の指し手を入力、**Then** 分岐として新しい子ノードが追加される

---

### User Story 2 - 戦型ラベルの付与と管理 (Priority: P1)

ユーザーは任意の局面（ノード）に対して戦型ラベル（例：「矢倉」「四間飛車」「角換わり」等）を付与できる。ラベルは自由に作成・編集・削除でき、1つの局面に複数のラベルを付与可能。

**Why this priority**: 定跡の分類・整理という本アプリケーションの差別化要因であり、学習効率向上の核となる機能。

**Independent Test**: 任意の局面にラベルを付与し、そのラベルで検索・フィルタリングできることを確認。

**Acceptance Scenarios**:

1. **Given** 定跡ツリー内の任意のノードを選択した状態、**When** ラベル追加を実行しラベル名を入力、**Then** そのノードにラベルが付与され視覚的に表示される
2. **Given** ラベルが付与されたノードを選択した状態、**When** ラベル一覧を表示、**Then** 付与されているすべてのラベルが確認できる
3. **Given** 複数の定跡ツリーとラベルが存在する状態、**When** 特定のラベルで検索、**Then** そのラベルが付与されたすべてのノードが一覧表示される

---

### User Story 3 - 定跡ツリーの視覚的表示と操作 (Priority: P2)

ユーザーは定跡ツリーを木構造またはフローチャート形式で視覚的に確認できる。ノードの展開・折りたたみ、特定ノードへのジャンプ、ツリー全体の俯瞰表示が可能。

**Why this priority**: 視覚的な操作性はユーザー体験の重要な要素だが、データの入力・管理機能が先に必要。

**Independent Test**: 50手以上の分岐を持つ定跡ツリーを視覚的に表示し、展開・折りたたみ・ナビゲーションができることを確認。

**Acceptance Scenarios**:

1. **Given** 分岐を含む定跡ツリーが存在する状態、**When** ツリー表示を選択、**Then** 木構造形式で全体が視覚的に表示される
2. **Given** 展開されたツリーを表示中、**When** 特定のノードを折りたたみ、**Then** そのノード以下のサブツリーが非表示になる
3. **Given** 大規模なツリーを表示中、**When** 特定のラベルが付いたノードへジャンプ、**Then** 該当ノードが画面中央に表示される

---

### User Story 4 - 定跡データのインポート・エクスポート (Priority: P2)

ユーザーは既存の棋譜データ（KIF/KI2形式）から定跡ツリーへ手順をインポートできる。また、作成した定跡ツリーを複数形式（JSON、KIF）でエクスポートできる。

**Why this priority**: 既存資産の活用とデータポータビリティは重要だが、まずコア機能の完成が優先。

**Independent Test**: KIF形式の棋譜ファイルをインポートし、その手順が定跡ツリーとして反映されることを確認。

**Acceptance Scenarios**:

1. **Given** KIF形式の棋譜ファイルがある状態、**When** インポートを実行、**Then** 棋譜の手順が定跡ツリーの分岐として追加される
2. **Given** 定跡ツリーが存在する状態、**When** エクスポートを実行、**Then** 指定形式でファイルが出力される
3. **Given** 既存の定跡ツリーがある状態、**When** 新しい棋譜をインポート、**Then** 共通する手順は既存ノードにマージされ、新しい手順のみが追加される

---

### User Story 5 - コメント・メモの追加 (Priority: P3)

ユーザーは任意のノード（局面）に対してコメントやメモを追加できる。学習時の気づきや参考文献の記録に活用する。

**Why this priority**: 学習補助機能として有用だが、コア機能ではない。

**Independent Test**: 任意のノードにコメントを追加し、後から確認・編集できることを確認。

**Acceptance Scenarios**:

1. **Given** 定跡ツリー内の任意のノードを選択した状態、**When** コメント追加を実行、**Then** テキスト入力欄が表示され入力・保存できる
2. **Given** コメントが存在するノード、**When** そのノードを選択、**Then** コメント内容が表示される

---

### Edge Cases

- 同一局面が異なる手順で到達した場合（転置）の扱いは？→ 合流を許可し、同一ノードとして扱う
- 反則手（二歩、打ち歩詰め等）の入力を試みた場合は？→ エラーを表示し入力を拒否
- 極端に大きな定跡ツリー（1000ノード以上）の場合のパフォーマンスは？→ 遅延読み込みと仮想スクロールで対応
- ラベル名に特殊文字が含まれる場合は？→ 許可するが、検索時は適切にエスケープ処理
- 定跡ツリーのマージ時にコンフリクトが発生した場合は？→ ユーザーがどちらの手順を採用するか選択可能
- 千日手（同一局面の繰り返し）の扱いは？→ 初期リリースでは検出せず通常のノードとして登録。将来のUI開発時に検出・警告機能を検討
- 定跡ツリーを削除した場合は？→ ゴミ箱に移動し、復元可能。30日後に自動削除
- 転置により複数の親を持つノードを削除する場合は？→ 選択した親からのエッジのみ削除（ノード自体は残る）。単一親のノードは通常通り子孫含め削除可能

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 平手の初期局面から定跡ツリーを新規作成できる
- **FR-002**: System MUST 任意のノードに対して合法手のみを子ノードとして追加できる
- **FR-003**: System MUST 同一局面から複数の分岐（応手）を登録できる
- **FR-004**: System MUST 定跡ツリーのデータを永続化し、再起動後も利用できる
- **FR-005**: System MUST 任意のノードに対してユーザー定義のラベルを付与できる
- **FR-006**: System MUST ラベルによるノードの検索・フィルタリング機能を提供する
- **FR-007**: System MUST 定跡ツリーを木構造形式で表現するデータ構造を提供する（視覚的描画はクライアント側責務）
- **FR-008**: System MUST 各ノードにおける局面（盤面と持ち駒）のデータを提供する（視覚的描画はクライアント側責務）
- **FR-009**: System MUST KIF形式およびKI2形式の棋譜ファイルからの手順インポートに対応する
- **FR-010**: System MUST 定跡ツリーを複数形式（JSON、KIF）でエクスポートできる。JSONはラベル等の独自データを含み、KIFは他アプリとの互換性を提供
- **FR-011**: System MUST 任意のノードにテキストコメントを追加できる
- **FR-012**: System MUST 同一局面への異なる手順経路（転置）を検出し、合流を許可する
- **FR-013**: System MUST 反則手の入力を検出しエラーを表示する
- **FR-014**: System MUST 同一局面を基点として、別の定跡ツリーの手順をマージできる（木構造維持、根方向への分岐増加不可）
- **FR-015**: System MUST マージ時にコンフリクト（同一局面から異なる手順が存在）が生じた場合、どちらを採用するかユーザーが選択できる
- **FR-016**: System MUST 定跡ツリー削除時にゴミ箱へ移動し、30日間保持後に自動削除または手動で完全削除できる
- **FR-017**: System MUST ゴミ箱内の定跡ツリーを復元できる

### Key Entities

- **定跡ツリー（Joseki Tree）**: 1つの定跡体系を表す。ルートノード、名前、作成日時、更新日時を持つ
- **ノード（Node）**: 木構造の1要素。局面情報、親ノード参照、子ノード参照リスト、ラベルリスト、コメントを持つ
- **局面（Position）**: 盤面の駒配置と両者の持ち駒の状態。SFEN形式等で一意に識別可能
- **指し手（Move）**: 親局面から子局面への遷移を表す。開始位置、終了位置、駒種、成り判定等を含む
- **ラベル（Label）**: 戦型や任意の分類を表すタグ。名前と色（任意）を持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

#### 初期リリース（API）で検証

測定条件: PostgreSQL ウォーム状態、単一リクエスト

- **SC-002**: 100ノード以上の定跡ツリーでも、API応答が1秒以内に完了する
- **SC-003**: ラベル検索により、1000ノード規模のデータからAPI応答が2秒以内に完了する
- **SC-005**: KIF形式の棋譜ファイル（100手程度）のインポートが3秒以内に完了する

#### 将来のUI開発時に検証
- **SC-001**: ユーザーは初手から20手程度の定跡分岐を5分以内に入力できる
- **SC-004**: ユーザーは初回利用時、チュートリアルなしで基本操作（ツリー作成、手順入力、ラベル付与）を10分以内に習得できる

## Assumptions

- ユーザーは将棋のルールと基本的な棋譜表記を理解している
- 初期リリースでは平手戦のみを対象とし、駒落ち対局は将来対応とする
- 初期リリースではUSIプロトコルによるAI評価値機能は含まない
- データ保存はローカルストレージを前提とし、クラウド同期は将来対応とする
- 初期リリースはREST APIのみを提供し、フロントエンド（Web UI）は後続開発とする
- 初期リリースはシングルユーザー前提（認証なし、ローカル実行）とし、マルチユーザー対応は将来検討
- 将来的な利用環境はデスクトップブラウザを想定するが、モバイル対応は将来検討

## Clarifications

### Session 2026-01-12

- Q: 複数の定跡ツリー間の関係性は？ → A: 基本的に完全独立。ただし同一局面を基点としたマージ機能を提供。マージ時は木構造を維持（根方向への分岐増加不可）、コンフリクト時はユーザー選択可能。千日手の扱いは将来検討。
- Q: 定跡ツリー削除時のデータ保護は？ → A: ゴミ箱に移動（一定期間後に自動削除、または手動で完全削除可能）
- Q: 初期リリースの提供形態は？ → A: REST APIのみ（フロントエンドは後続開発）
- Q: ユーザー管理と認証は？ → A: シングルユーザー（認証なし、ローカル実行前提）
- Q: エクスポート形式は？ → A: 複数形式対応（JSON + KIF）。KIFで他アプリとの互換性を確保し、JSONでラベル等の独自データを保持
- Q: 初期リリース（APIのみ）での視覚表示要件の扱いは？ → A: APIは視覚表示に必要なデータ構造を提供し、実際の描画はクライアント側責務。FR-007/FR-008は将来のUI開発時に検証
- Q: 成功基準のAPI適合性は？ → A: SC-001/SC-004（UI操作前提）は将来のUI開発時に検証。初期リリースはAPI応答時間（SC-002/SC-003/SC-005）で評価
- Q: インポート対象の棋譜形式は？ → A: KIF + KI2形式（KI2はKIFの派生で実装コスト低）。CSA形式は将来検討

### Session 2026-01-12 (Pre-tasks)

- Q: 千日手（同一局面の4回繰り返し）が入力された場合の扱いは？ → A: 初期リリースでは検出せず通常のノードとして登録。将来のUI開発時に検出・警告機能を検討
- Q: ゴミ箱内の定跡ツリーは何日後に自動削除するか？ → A: 30日後に自動削除
- Q: 転置により複数の親を持つノードを削除する場合の扱いは？ → A: 選択した親からのエッジのみ削除（ノード自体は残る）。単一親のノードは通常通り子孫含め削除可能
- Q: API応答時間の成功基準を測定する際の前提条件は？ → A: PostgreSQL ウォーム状態、単一リクエスト
- Q: コメント内のテキスト検索（全文検索）は初期リリースのスコープに含めるか？ → A: 含めない（スコープ外）

## Scope Exclusions（スコープ外）

- 対局機能（本アプリケーションは定跡管理に特化）
- コメント内テキストの全文検索（ラベル検索で分類・検索ニーズを満たす）
- AIによる局面評価値の算出・記録
- リアルタイムの複数ユーザー共同編集
- 棋譜のオンライン共有機能
- モバイルネイティブアプリケーション
- ユーザー認証・マルチユーザー対応（初期リリース）
